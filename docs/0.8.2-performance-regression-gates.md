# 0.8.2 item-list and workspace-access performance gates

This review records the release decision and repeatable regression gates for
WI-613 and WI-614. It supersedes the earlier interpretation of the 100-worker
PostgreSQL runs as normal endpoint latency: those runs intentionally exceeded
the 30-connection pool and primarily measured queueing.

## Normal-concurrency PostgreSQL baseline

The WI-613 profile ran on 2026-07-15 with PostgreSQL 17, 100 workspaces,
5,000 items, 500 completed items, 20 newer history rows per completed item,
page 80, five workers, and a 20-second measured window.

| Scenario | p50 | p95 | p99 | Mean list SQL |
| --- | ---: | ---: | ---: | ---: |
| Completed since | 52 ms | 64 ms | 73 ms | 13.424 ms |
| Deep page | 57 ms | 71 ms | 78 ms | 22.214 ms |

The run completed 1,812 operations at 90.39 requests/second with zero errors,
zero pool waits, and a 0.221% session-validation database-load ratio. The
partial current-status index handled 4,399,255 scans; the legacy history index
handled none. The completed-since count SQL averaged 2.781 ms.

The WI-614 1,000-workspace baseline at the production per-user ceiling of 16
workers recorded 24/31/35 ms p50/p95/p99 and 659.59 requests/second across
13,203 operations, with zero errors and zero pool waits. Its session-validation
database-load ratio was 0.030%. An earlier run recorded 51/69/80 ms and 303
requests/second, also without pool waits.

## Enforced gates

`make performance-regressions` executes each benchmark three times and fails
when any run exceeds its ceiling:

| Path | Time | Bytes | Allocations | Structural invariant |
| --- | ---: | ---: | ---: | --- |
| Current-status lookup over 10,000 history rows | 100 us/op | 4 KiB/op | 100 allocs/op | Uses the partial current-status index |
| Accessible workspace snapshot at 1,000 workspaces | 1 ms/op | 1 MiB/op | 10,000 allocs/op | Exactly one permission decode/op |

The ceilings intentionally leave substantial shared-runner headroom while
remaining far below the removed 320 us history scan and 83 ms/O(workspaces)
permission path. GitHub Actions runs the target as a blocking job.

The HTTP regression profile separately fails normal-concurrency runs above
250 ms p95, 500 ms p99, any database-pool wait, 1% request errors, or a 2%
session-validation database-load ratio. Runs above pool capacity remain
diagnostic saturation tests and do not apply latency or pool-wait gates.

## Search and pagination decision

Text search still uses case-insensitive `%term%` matching. PostgreSQL trigram
or full-text indexing is not included in 0.8.2 because the release profiles do
not identify search as a pool or tail-latency release gate, and changing it
would require an explicit SQLite/PostgreSQL ranking and tokenization contract.
Revisit indexed search when a dedicated, rate-limit-aware profile exceeds the
250 ms p95 gate at representative production cardinality.

Deep OFFSET pagination is also retained for 0.8.2. Page 80 at 5,000 items is
well below the gate and its list SQL averaged 22.214 ms. Keyset pagination would
change arbitrary system/custom-field sorting and backward-navigation contracts;
introduce it only when a measured deep-page profile crosses the gate or the
supported cardinality materially increases.

These are explicit defer decisions, not assumptions that either technique is
universally unnecessary. The regression profiles provide the trigger for
reopening them.
