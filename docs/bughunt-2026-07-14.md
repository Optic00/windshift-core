# Bug Hunt — 2026-07-14

## Scope and method

This is a fresh review of the current working tree, including its existing uncommitted changes. I traced authentication, user deactivation, timers, and worklog flows, then cross-checked prior bug-hunt reports so the table focuses on currently reachable defects rather than already-fixed historical issues. No source fixes are included in this review.

## Findings

| # | Severity | Area | Finding | Trigger and impact | Evidence | Recommended fix |
|---:|:---:|---|---|---|---|---|
| 1 | High | REST API / authorization | Numeric `item_id` bypasses item authorization when creating a worklog. | A bearer-token user with `time:write` and project access can submit any positive item ID. The API checks `item_key`, but copies a numeric ID directly, allowing a worklog to be attached to an item the caller cannot view. | `internal/restapi/v1/handlers/time_worklogs.go:273-296` | Resolve both identifier forms through one authorization-aware lookup and return a generic not-found response when the item is inaccessible. |
| 2 | High | REST API / data disclosure | The v1 worklog list exposes item metadata after item access is lost. | Worklogs remain visible to their owner, but the v1 response returns joined item title, workspace ID/key, and item number without rechecking `item.view`. A revoked user can therefore continue reading restricted item metadata. | `internal/restapi/v1/handlers/time_worklogs.go:137-147`; `internal/repository/time_worklog_repository.go:69-84,115-130` | Apply the same permission-aware redaction used by the cookie-auth worklog handler, preferably in a shared response mapper. |
| 3 | High | Timers / data disclosure | Active-timer read and stop responses leak linked item/workspace metadata after access is revoked. | If access is removed while a timer is running, polling the timer still returns the joined title/workspace fields. Stop correctly drops the item association from the new worklog, but copies the stale metadata into its response. | `internal/repository/active_timer_repository.go:122-152`; `internal/restapi/v1/handlers/timers.go:90-106`; `internal/handlers/active_timers.go:52-68,89-99`; `internal/services/timer_service.go:208-226,271-279` | Redact linked metadata on every timer response when the caller no longer has item access; do not copy repository-enriched fields after the permission check fails. |
| 4 | High | LDAP / account security | LDAP auto-deactivation skips the normal security-offboarding path. | When a user disappears from LDAP, synchronization only sets `users.is_active = false`. Cached sessions and API-token validations can remain accepted until cache expiry, while owned agent users and their tokens are not deactivated/revoked at all. | `internal/ldap/sync.go:115-126,261-264`; `internal/server/server.go:480-496,1139-1142` | Route LDAP deactivation through the same centralized transaction and cache invalidation used by administrative deactivation, including owned-agent cleanup. |
| 5 | High | SCIM / API tokens | SCIM deactivation deletes token rows without invalidating the token-validation cache. | A recently validated owner or agent bearer token can continue authenticating for the token cache TTL (30 seconds) after SCIM deactivation, because the SCIM cascade omits `TokenManager.InvalidateTokens`. | `internal/server/server.go:489-493,518-530`; `internal/services/user_deactivate.go:85-108`; `internal/handlers/scim.go:1834-1856`; `internal/auth/tokens.go:368-376,423-448,785-800` | Invalidate every revoked token returned by the cascade, and centralize deactivation so each entry point cannot omit a security side effect. |
| 6 | Medium | Timers / availability | A timer can start on a customerless project but can never stop cleanly. | Start validates booking permission and project status, not the required customer. Stop scans nullable `customer_id` into an integer and fails before finalization, so the timer remains active and the one-timer-per-user constraint prevents starting another timer. | `internal/services/timer_service.go:71-103,233-236`; `internal/repository/active_timer_repository.go:25-43,94-119` | Reject timer start when the project has no customer, make the stop lookup nullable-safe, and provide a safe cancellation path for already-wedged timers. |
| 7 | Medium | Worklogs / validation | v1 and AI worklog creation accept out-of-range `HH:MM` values. | Inputs such as `25:00` or `12:99` pass split/integer parsing. `time.Add` normalizes them into another day while the persisted worklog date remains the requested date, producing inconsistent reporting data. | `internal/restapi/v1/handlers/time_worklogs.go:240-262`; `internal/aitools/time.go:297-315` | Use a shared strict parser such as `time.Parse("15:04", value)` and reject values outside the documented clock range. |
| 8 | Medium | Worklogs / integer safety | Unbounded `duration_minutes` can overflow `time.Duration`. | Both creation paths multiply an arbitrary positive integer by `time.Minute`. A sufficiently large value wraps the nanosecond duration, allowing a positive stored duration with an end timestamp before the start timestamp. | `internal/restapi/v1/handlers/time_worklogs.go:236-239`; `internal/aitools/time.go:293-296` | Enforce a business maximum and perform a checked conversion before multiplication in one shared validator. |
| 9 | Medium | Email verification / sessions | Successful email verification leaves cached session state stale. | The database is updated, but the user's session-validation cache is not invalidated. Until the cache expires, authenticated endpoints can still treat the user as unverified and `/api/auth/me` can report the old value. | `internal/services/email_verification.go:122-136`; `internal/handlers/auth.go:584-610`; `internal/middleware/auth.go:424-445`; `internal/auth/session_validation.go:28-44,296-320` | Invalidate the user's session-validation entries immediately after the verification transaction commits. |
| 10 | Medium | Session cache / availability | Targeted session invalidation also invalidates every user's cached session. | Cache entries share a global epoch. Logout, refresh, and user-specific invalidation increment that epoch, making all unrelated entries stale and forcing database reloads; under ordinary session churn this can create a cache-miss storm while stale entries remain allocated until visited or expired. | `internal/auth/session.go:174-182,207-220`; `internal/auth/session_validation.go:296-320,354-365,382-413` | Reserve the global epoch for full resets. Delete targeted keys without changing it, and use per-token or per-user generations to guard against in-flight stale loads. |

Findings 1 and 2 are separate authorization failures: the first permits an unauthorized association at write time, while the second discloses metadata at read time. They affect the newer bearer-token v1 surface even though the analogous cookie-auth paths have permission checks or redaction.
