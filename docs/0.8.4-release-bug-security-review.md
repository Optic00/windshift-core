# Windshift 0.8.4 release bug and security review

Date: 2026-07-30
Candidate: `064a820d` (`main`, `origin/main`)
Comparison base: `v0.8.3`

## Release decision

**Go with acknowledged residual risks after the 2026-07-30 remediation.**

The original review identified three potential release blockers. Their current
disposition is:

1. **SEC-084-01: accepted risk.** The release owner concluded that the Web Push
   SSRF validation gap is not severe enough to block 0.8.4. No code change was
   made for this finding.
2. **BUG-084-02: resolved.** Reuse of a milestone release idempotency key now
   requires an exact match with the durable original request and returns
   `409 Conflict` on payload drift.
3. **BUG-084-03: resolved.** Jira conflict detection and enqueue are serialized
   atomically per connection; active overlaps cannot be forced, while completed
   history can still be deliberately reimported.

Three additional medium/low findings should be triaged for the release. No
called Go dependency vulnerabilities or high-severity production npm
vulnerabilities were reported by the dependency scanners.

## Scope

There is no `v0.8.4` tag yet. This review therefore treats
`v0.8.3..064a820d` as the release candidate:

- 30 commits
- 362 files changed
- 26,958 insertions and 14,703 deletions

The review emphasized authorization, public routes, outbound network access,
idempotency, concurrent/background work, data ownership, migrations, Jira
import fidelity, public forms, and dependency risk.

## Findings

### SEC-084-01 — High — Web Push SSRF protection has validation/use gaps

**Status: Accepted risk; not a 0.8.4 release blocker by release-owner
decision.**

**Affected code**

- `internal/services/push_service.go:163-196`
- `internal/services/push_service.go:329-339`
- `internal/services/push_service.go:363-377`
- `internal/services/push_service.go:531-590`

**Evidence**

`Subscribe` validates the submitted endpoint once and persists the original
hostname. Delivery later loads that stored endpoint and passes it to
`webpush.SendNotificationWithContext` without revalidation. The HTTP client
uses the default transport; its only SSRF-specific control is `CheckRedirect`,
which does not run for the initial connection and does not constrain the IP
selected by the transport.

This leaves two gaps:

1. Unsafe subscription rows created before the 0.8.4 validation change remain
   active after upgrade and are delivered without validation.
2. A hostname can resolve to public IPs during subscription validation and to a
   non-public IP when the transport resolves it again for delivery (DNS
   rebinding/time-of-check-to-time-of-use).

The request is HTTPS and normal certificate validation still applies, which
limits the set of reachable targets, but it does not make the network boundary
safe. Internal services using publicly trusted certificates, split DNS, or
legacy directly stored endpoints remain reachable candidates. At minimum this
permits blind reachability/timing probes from the Windshift server.

**Required fix**

- Revalidate every stored endpoint immediately before delivery and revoke
  invalid legacy rows.
- Use a dedicated `http.Transport.DialContext` that resolves the destination
  and rejects every non-public address at connection time. Apply the same rule
  on each redirect.
- Prefer connecting to a validated/pinned address while preserving the original
  hostname for TLS SNI and certificate verification.
- Consider a one-time migration or startup cleanup for legacy unsafe rows.

**Required regression coverage**

- Seed a private/loopback endpoint directly in `push_subscriptions` and prove
  dispatch refuses it without invoking the sender.
- Exercise a resolver that returns a public address during validation and a
  private address during dialing.
- Cover redirect validation with the same dial-time transport, for both IPv4
  and IPv6.

Current tests validate subscription input and redirect URLs only:
`../core-tests/internal/services/push_endpoint_validation_test.go`.

### BUG-084-02 — High — Milestone idempotency keys accept payload drift

**Status: Resolved in the 2026-07-30 working tree.**

**Affected code**

- `internal/services/planning_milestones.go:745-861`
- `internal/handlers/milestones.go:754-825`

**Evidence**

The first request stores the release payload in `milestone_releases`.
On an idempotency-key conflict, `BeginMilestoneRelease` reads only `id` and
`state`; it neither reads nor compares the stored tag, repository, connection,
name, body, flags, or target commit.

If the first provider call is uncertain, a retry reclaims that row with
`NeedsReconcile`. The handler then reconciles and creates using the *new*
request's repository and payload. `CompleteMilestoneRelease` updates only the
remote ID/URL and state, leaving the original stored tag and metadata in place.

Example:

1. Request key `K` creates a pending record for tag `v1`; the provider call
   times out and the row becomes `reconciliation-required`.
2. A retry uses key `K` but changes the request to tag `v2` or a different
   linked repository.
3. The handler reconciles/creates `v2`, then stores its remote ID and URL on the
   local row whose durable metadata still describes `v1`.

This breaks the core idempotency contract and can create or associate the wrong
SCM release. The generated fallback key includes the payload, but clients that
provide the supported `Idempotency-Key` header are affected.

**Resolution**

- `BeginMilestoneRelease` now loads the durable tag, name, body, flags, target
  commit, SCM connection/repository, and creator whenever the unique key
  already exists.
- Every stored request field must match before the attempt can return a prior
  result or reclaim a reconciliation lease.
- Payload drift returns `ErrMilestoneReleaseIdempotencyConflict`; the HTTP
  handler maps it to an exact `409 CONFLICT` response before any provider call.

**Regression coverage**

- `../core-tests/internal/services/planning_milestone_release_test.go:121`
  checks every durable request field and verifies the original uncertain row is
  unchanged.
- `../core-tests/internal/handlers/milestones_test.go:113` asserts the exact
  handler-level `409` contract.
- The existing identical-request reconciliation and concurrent-lease tests
  remain passing.

### BUG-084-03 — High — Concurrent Jira imports can mutate the same scope

**Status: Resolved in the 2026-07-30 working tree.**

**Affected code**

- `internal/handlers/jira_importer.go:397-532`
- `internal/handlers/jira_importer.go:572-641`

**Evidence**

The conflict query includes every overlapping job except `data_deleted`,
including `queued` and `running` jobs. However, `force_reimport=true` bypasses
all returned conflicts and immediately inserts another queued job.

For normal requests, conflict detection and job insertion are separate database
operations with no transaction, lease, advisory lock, or unique active-scope
constraint. Two simultaneous requests can both observe no conflict and both
insert a job. The schemas index connection and status separately but permit
unbounded duplicate active jobs for the same connection/project scope.

The test suite explicitly pins this permissive SQL behavior and leaves the
intended guard test skipped:
`../core-tests/internal/handlers/jira_idempotency_test.go:9-58`.

Concurrent import goroutines can update the same workspaces and items, transfer
mapping ownership, create duplicate dependent records, and make later cleanup
depend on whichever job wrote last. This is a data-integrity risk even when
both requests come from an authorized administrator.

**Resolution**

- Enqueue now runs in one database transaction.
- A no-op update of the existing Jira connection row provides a short
  transaction lock. PostgreSQL serializes on that row; SQLite uses its
  immediate transaction and dedicated write connection.
- Conflict detection runs after the lock and the queued job is inserted before
  the transaction commits, removing the check/insert race.
- Any overlapping `queued` or `running` job returns
  `409 JIRA_IMPORT_CONFLICT`, even when `force_reimport=true`.
- Force reimport remains allowed for completed historical jobs, and disjoint
  project sets on the same connection remain allowed.

**Regression coverage**

- `../core-tests/internal/handlers/jira_idempotency_test.go:12` verifies the
  handler denial contract and active-job details.
- `../core-tests/internal/handlers/jira_idempotency_test.go:50` starts two
  synchronized enqueue attempts and proves exactly one job is created.
- `../core-tests/internal/handlers/jira_idempotency_test.go:106` covers
  overlapping subsets and disjoint project sets.
- `../core-tests/internal/handlers/jira_idempotency_test.go:154` proves a
  completed import may still be forced and is recorded as provenance.

### SEC-084-04 — Medium — Public form drafts persist and cross user boundaries

**Affected code**

- `frontend/src/lib/features/forms/publicFormDrafts.js:1-46`
- `frontend/src/lib/features/forms/FormRenderer.svelte:96-119`
- `frontend/src/lib/features/forms/FormRenderer.svelte:138-149`

**Evidence**

Every non-empty public form draft is automatically written to origin-wide
`localStorage`, including title, description, and all custom-field values.
`updated_at` is recorded but never checked, so drafts do not expire. The key is
only form slug plus form ID; it is not bound to an authenticated identity,
browser session, or anonymous visitor.

On a shared browser, the next person who opens the same form automatically
receives the previous person's draft values. Public service, HR, security, and
support forms can contain personal or confidential information. Any script
executing on the same origin can also read the persistent values.

**Required fix**

- For anonymous forms, prefer `sessionStorage` or an explicit opt-in
  “save on this device” control.
- Apply a short expiry and delete expired values during load.
- Bind authenticated drafts to the current user and clear them on logout or
  account change.
- Allow sensitive form fields/forms to disable persistence, and disclose local
  persistence to the user.
- Catch storage access/write failures so restricted browser modes do not break
  form editing.

**Required regression coverage**

- Expired drafts are removed and not restored.
- Anonymous drafts do not survive a new browser session by default.
- Drafts from one authenticated user are not loaded for another.
- Storage API failures leave the form usable.

Current tests intentionally verify round-tripping every editable value but do
not cover expiry or identity/session isolation:
`../core-tests/frontend/src/lib/features/forms/publicFormDrafts.test.js`.

### BUG-084-05 — Medium — Jira mapping write failures are reported as success

**Affected code**

- `internal/handlers/jira_importer.go:969-992`
- `internal/handlers/jira_importer.go:1461-1497`
- `internal/handlers/jira_import_entities.go:1347-1359`
- `internal/handlers/jira_import_entities.go:1789-1805`

**Evidence**

`recordMapping` returns no error. If its insert/upsert fails it only logs and
the import continues. Callers may count the entity as imported and continue
building dependent data even though `jira_import_id_mappings` is the durable
provenance used for later relationship work and cleanup.

Reimport makes the failure mode worse: it first changes the previous mapping to
`was_created=false` and records `superseded_by_job_id`, then separately calls
the fallible, error-swallowing `recordMapping`. If that second write fails, the
old job has relinquished cleanup ownership and the current job has no mapping.
The imported entity can become unowned and impossible for normal import cleanup
to remove.

**Required fix**

- Make `recordMapping` return an error and propagate it to the job result.
- Put the entity mutation, old-ownership transfer, and new mapping upsert in one
  transaction where practical.
- Do not increment imported counts or run mapping-dependent phases after a
  provenance write failure.

**Required regression coverage**

- Inject a mapping insert failure and assert that the import/job fails.
- During reimport, prove a failed new mapping rolls back the old ownership
  transfer and entity mutation.
- Cover item, comment, watcher, and relationship mapping paths.

### BUG-084-06 — Low — New Jira workflow/screen capture payloads are discarded

**Affected code**

- `internal/handlers/jira_capture.go:50-66`
- `internal/handlers/jira_capture.go:123-145`
- `internal/handlers/jira_capture.go:267-305`

**Evidence**

The recording client calls `appendJSONL` with:

- `jira_project_workflow_configuration.jsonl`
- `jira_project_screen_configuration.jsonl`

Neither filename is present in the `jsonlPaths` allowlist initialized by
`newRecordingClient`. `appendJSONL` therefore logs “Unknown Jira capture JSONL
target” and returns without writing either response.

This does not affect the live import itself, but silently removes the new
workflow/screen fidelity inputs from `JIRA_CAPTURE_PAYLOADS`, reducing the
usefulness of release debugging and replay captures.

**Required fix**

- Add both files to the initialized allowlist and truncate them with the other
  capture files.
- Add a recording-client test that invokes both methods and asserts exact JSONL
  output.

No current handler test exercises these recording-client methods.

## Recommended release sequence

1. Carry SEC-084-01 as the explicitly accepted, non-blocking risk.
2. Fix SEC-084-04 and BUG-084-05, or explicitly document and accept their
   privacy/data-integrity risk before release.
3. Fix BUG-084-06 alongside the Jira work because it is small and restores the
   intended diagnostic capture.
4. Run PostgreSQL variants, focused Playwright public-form/Jira flows, and a
   `v0.8.3` database upgrade rehearsal.
5. Repeat dependency scans, then tag after reviewing the remaining accepted
   risks.
