# Frontend accessibility audit — SOFT-34

**Date:** 2026-08-12  
**Scope:** `frontend/src`, `frontend/index.html`, and shared frontend components.  
**Method:** Static source review using Svelte markup/component inspection and repository searches. This is a risk-oriented audit, not a substitute for browser testing with NVDA/JAWS/VoiceOver, keyboard-only testing, or axe/WAVE against authenticated and public routes. Findings are prioritized by likely user impact and remediation effort.

## Executive summary

The frontend has a solid accessibility foundation in several shared primitives: semantic buttons are used widely, images generally have `alt` attributes, dialogs use `role="dialog"`/`aria-modal`, `ModalBackdrop` implements focus entry, focus trapping, Escape handling, and focus restoration, and reduced-motion handling is present in the design system and several feature areas.

The principal risks are inconsistent labeling in forms, custom interactive elements that are not consistently represented as native controls, incomplete ARIA state/relationship wiring for custom pickers and tabs, and interaction patterns that rely on hover or mouse events. These issues are spread across reusable components, so fixing the shared primitives should yield the highest return.

## Findings

| ID | Priority | WCAG area | Evidence | User impact | Recommendation |
|---|---|---|---|---|---|
| A11Y-01 | High | 1.3.1, 3.3.2, 4.1.2 — labels and names | Many usages of the shared `<Input>` component provide only a `placeholder`, e.g. `frontend/src/lib/pages/UserProfile.svelte:918-921` (`Username`, `Email`, `First name`, `Last name`). `Input.svelte` exposes `ariaLabel`, but does not require or automatically associate a visible label. Similar patterns occur across dialogs/settings. | Screen-reader users may hear no durable field name; placeholders disappear once typing begins and are not an adequate label. | Add/standardize a labeled field primitive (`label for={id}` plus description/error wiring). Require an accessible name for shared inputs in review/lint. Replace placeholder-only usages, starting with account/agent creation and high-traffic forms. |
| A11Y-02 | High | 2.1.1, 4.1.2 — keyboard and semantics | `frontend/src/lib/components/Card.svelte:92-94` and `Panel.svelte:54` attach `onclick` to a plain `<div>` and explicitly suppress Svelte a11y warnings. Similar click-only/static-element suppressions are numerous. `DataTable.svelte:174-176` makes sortable headers clickable without an evident button control; rows also use click handlers (`:197-200`). | Keyboard users cannot reliably discover or activate all actions; assistive technology receives a non-interactive role for an interactive surface. | Use native `<button>`/`<a>` for actions. For genuinely clickable cards/rows, provide a keyboard-operable control inside the content (or a carefully implemented `role="button"`, `tabindex="0"`, Enter/Space handling, and name). Make sortable headers buttons with `aria-sort`. Remove warning suppressions where possible. |
| A11Y-03 | High | 2.1.1, 4.1.2 — custom picker keyboard model | `frontend/src/lib/pickers/BasePicker.svelte:474-490` uses a `role="combobox"` `<div>` with custom key handling; the multiple-select wrapper is `role="button" tabindex="-1"` (`:502-514`). Option rows are `<div>` elements with click handlers (`:581+`), while some creation options are separately `role="button"`. | Focus order and semantics vary by picker mode. A tabindex of `-1` makes a wrapper unavailable to sequential keyboard navigation, and custom listbox behavior is difficult for screen readers to interpret consistently. | Align with the WAI-ARIA combobox/listbox pattern: one focusable combobox input, stable `aria-controls`, `aria-activedescendant`, `aria-expanded`, and option IDs/states. Prefer native controls where possible. Add keyboard tests for open, search, arrow navigation, selection, clear, and create. |
| A11Y-04 | High | 4.1.2 — dialog naming | `frontend/src/lib/components/ModalBackdrop.svelte:163-169` always renders `role="dialog"` and `aria-modal="true"`, but `aria-labelledby` is optional. Several loading/error/customization overlays in `MainAppOverlays.svelte:69-106` use `ModalBackdrop` without `ariaLabelledBy`; `LazyRootDialog.svelte` has similar loading/error paths. | A screen reader may announce an unnamed dialog, or a loading overlay may expose no useful context. | Ensure every modal has a visible heading with a unique ID and pass `ariaLabelledBy`; use `role="status"`/`aria-live` for non-modal loading states that do not require dialog behavior. Add a development assertion or component API that requires a label for modal content. |
| A11Y-05 | Medium | 1.3.1, 4.1.2 — form label association | `frontend/src/design-system/viewer/pages/Tooltip.svelte:90-103` displays a `<label>` for “API Key” but does not provide `for`/`id` association. `NavigationMock.svelte:279-286` wraps a search input in a label but has no accessible name beyond placeholder text. These are design-system examples, but they model patterns likely to be copied. | Assistive technology may not associate the visible label with the control. | Give every labelable control an ID and use `for`, or nest the control directly in the label. Add examples and checks to the design-system guidance. |
| A11Y-06 | Medium | 1.3.1, 4.1.2 — tabs and state | Shared `TabNav.svelte`/`Tabs.svelte` render tab-like buttons, but the audit search did not find consistent `role="tablist"`, `role="tab"`, `aria-selected`, and `aria-controls` wiring across these primitives. | Users of screen readers may not know which tab is active or which panel is controlled; keyboard tab navigation may be less efficient than the expected arrow-key model. | Implement one tested tabs primitive with the ARIA tabs pattern (or use a native navigation pattern if panels are not true tabs), including active state and panel relationships. |
| A11Y-07 | Medium | 1.4.11, 1.4.3 — focus visibility and contrast | The codebase uses many `text-[var(--ds-text-subtle)]`, disabled opacity, hover-only controls, and inline colors. Some shared controls have visible focus rings, but static review cannot establish contrast for every theme/token combination. `WeeklyCalendar.svelte:1131-1133` includes a remove button hidden with `opacity-0 group-hover`, and multiple settings controls use similar hover-only visibility. | Low-vision users may miss focus/controls; keyboard users may be able to focus controls that are visually invisible. | Verify all light/dark semantic tokens with a contrast checker (4.5:1 normal text, 3:1 large text and non-text focus indicators). Keep actionable controls visible on focus (`focus-within:opacity-100`) and avoid opacity-only hiding. Test forced-colors mode. |
| A11Y-08 | Medium | 2.1.1, 2.4.7 — focus order and keyboard reachability | `MilkdownEditor.svelte:673-726` sets toolbar buttons to `tabindex="-1"`; `BasePicker.svelte` uses custom focus management and hidden/transparent inputs. Some components intentionally suppress a11y warnings for mouse event containers. | Important editor and picker functions may be skipped or difficult to reach without a mouse, especially when focus is moved into a rich-text editor. | Document the intended roving-tabindex model and ensure arrow-key navigation is implemented and announced. Verify every `tabindex="-1"` control is reachable via a documented keyboard path and has a visible focus state. |
| A11Y-09 | Medium | 1.3.1, 4.1.2 — data tables and charts | Many tables are present, but static inspection found no universal guarantee of table captions/accessible names and header `scope`. `Chart.svelte` contains an SVG chart (`:280+`) while several other charts provide `role="img"` and `aria-label`. | Complex tables/charts can be ambiguous or inaccessible when visual layout is removed. | Establish a shared table/chart accessibility contract: caption or `aria-labelledby`, scoped headers, sortable state, and a text summary/data table for charts. Ensure every SVG is either labeled or explicitly `aria-hidden="true"`. |
| A11Y-10 | Low | 1.1.1 — non-text content | Several avatar/logo images intentionally use `alt=""` (for example `WorkspacePicker.svelte:85`, `UserManager.svelte:736`, `PortalHeader.svelte:306`). This is appropriate only when adjacent text fully conveys the same information. | If adjacent names are absent or hidden, users lose identity/context conveyed by the image. | Confirm each empty alt is decorative/redundant. Otherwise use a meaningful localized alt (for example, workspace/user name). Keep decorative logos empty when the same brand name is nearby. |

## Positive controls observed

- `frontend/src/lib/components/ModalBackdrop.svelte` saves/restores focus, moves focus into the overlay, traps Tab/Shift+Tab, supports Escape, and uses `aria-modal`.
- Shared controls such as `Button.svelte`, `Toggle.svelte`, `Checkbox.svelte`, `Spinner.svelte`, and `NativeSelect.svelte` generally use native semantics and/or accessible names.
- The application shell declares `<html lang="en">` in `frontend/index.html` and provides a viewport configuration.
- Reduced-motion support exists in `frontend/src/design-system/animations.css` and multiple feature stylesheets; the boot/recovery animation also handles `prefers-reduced-motion`.
- Icon-only actions are frequently given localized `aria-label`s, particularly in navigation, pickers, editors, and mobile views.

## Recommended remediation order

1. Fix shared form labeling and error/description association (A11Y-01, A11Y-05).
2. Replace or remediate click-only `div` patterns and sortable/table interactions (A11Y-02).
3. Standardize and test the picker/combobox implementation (A11Y-03).
4. Require names on every modal and distinguish modal dialogs from status overlays (A11Y-04).
5. Consolidate tabs, table, chart, contrast, and focus rules into reusable primitives and automated checks (A11Y-06 through A11Y-10).

## Validation plan

- Run `npm run check` and `npm run typecheck` after remediation.
- Add component tests with Testing Library for labels, keyboard-only dialog/picker workflows, focus restoration, tab state, and sortable tables.
- Run axe-core (or equivalent) against representative authenticated routes, public board/portal routes, mobile routes, design-system examples, and every modal/picker state.
- Manually test keyboard-only navigation, 200% zoom/reflow, reduced motion, Windows High Contrast/forced colors, and at least one screen reader on both themes.
